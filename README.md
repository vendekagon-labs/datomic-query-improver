# Datomic Query Optimizer

## Rationale

Sometimes people new to Datomic datalog write queries that are not performant.
Other times queries are generated by application logic and it's much simpler to generate them naively, and let some other part of the application decide how to improve the query later.
In other cases, the optimal form for a Datomic query might change over the lifetime of an application, i.e. due to real changes in the domain data being tracked, the addition of batch jobs, etc.
Slow queries can significantly impact service health, dev and data science feedback cycles, etc., so query performance is a justified optimization target.

This project provides a "good enough" Datomic query improver based on two heuristics to handle these problems. The logic helps avoid basic mistakes, rather than finding unique high performance edge cases.
If you are writing awesome Datomic queries, it won't likely make them more awesome and might make some of them less awesome.
If you're writing or generating bad Datomic queries, it will probably make them significantly less bad, and might make a large set of them awesome.

## The Heuristics

Two heuristics are used. Both are described in the Datomic docs: [join along](https://docs.datomic.com/on-prem/best-practices.html#join-along)
and [most selective clause first](https://docs.datomic.com/on-prem/best-practices.html#most-selective-clauses-first).
These two heuristics are applied in this order to any where clause. Treating the original query's `:where` clauses as an unordered set from which to draw the next `:where` clause:

(1) Rank clauses by number of new variables introduced.
(2) For all clauses that introduce the fewest new variables, pick the clause estimated to match the fewest datoms.

If a query contains arguments to `:in` (including collection and tuple bindings), those are used as the initial bindings.
Otherwise, the first clause will be chosen based on criteria (2).
Each clause is then added in order to build a logical ordering based on this sort (determined by bindings introduced in relation to previous clauses).
Exact ties keep the clauses' original relative order.

A clause is only placed once the variables it needs are bound: the inputs of a predicate or function expression,
all variables of a `not`, the join variables of a `not-join`, and for `or`, `or-join` and rule invocations
(whose bindings depend on rule definitions), whichever of their variables were bound at their position in the
original query. So a valid query stays valid.

The datom estimate for (2) uses statistics per attribute, in either of two forms:

- a datom count per attribute, e.g. from the Datomic client API's `db-stats` (see `db-stats->attr-counts`)
- a map of `{:count :distinct-values :distinct-entities}` per attribute. With these, a clause whose entity or
  value is already bound (or a constant) is estimated at the datoms per entity or per value, rather than the
  attribute total. An example of computing and storing them with the peer API is in `dev/statistics.clj`;
  they're updated lazily using `datoms` and stored in the database.

The estimate is also reduced for each pending filter a clause would let run next (e.g. `[?t :track/duration ?d]`
when `[(< ?d 269)]` is waiting on `?d`), assuming System R's classic selectivities: 1/3 for a predicate and 9/10
for `not`/`not-join`.

## Running the tests

```
clojure -M:test
```

The tests run against an in-memory Datomic database with skewed synthetic data (`com.datomic/peer` is a
dependency of the `:test` and `:dev` aliases only). Query cost is measured deterministically as the rows produced
by each clause, per Datomic's `:query-stats`. Besides examples of complicated query forms, generated queries are
checked to stay equivalent under suggestion, and for a set of generated queries every ordering of their clauses
is measured to check that suggesting from the worst ordering does close to as well as the best one.
